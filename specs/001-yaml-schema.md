# 原本 YAML スキーマ定義 (001-yaml-schema)

## 1. 概要とユーザーストーリー

- **ユーザーストーリー**:
  - **As a**: コーディングエージェントおよび開発チームの計画担当者
  - **I want**: メンバ情報（稼働上限・スキル）、タスク情報（見積工数・依存関係・期限）、およびチームカレンダー（祝日・非稼働日）をテキストベースの YAML 原本として定義したい
  - **So that**: Excel 等の手作業に頼らず、テキストファイルとして計画条件をバージョン管理し、エージェントが自動でスケジュールを計算・再計画できるようにするため
- **背景と目的**:
  Taskweave では、計画の前提（原本データ）と計算結果（生成スケジュール）を厳密に分離します。原本データを関心事ごとに明確な YAML スキーマとして定義することで、人間と AI エージェントの双方が Git 差分を通じて安全かつ容易に編集・保守できるようにします。

---

## 2. 要件定義

### 2.1 機能要件 (FR: Functional Requirements)

- **FR-1 (ファイル分割構成)**: 原本データは関心事に応じて以下の 3 つの YAML ファイルに分割して管理できること。
  - `members.yaml`: チームメンバの基本情報、稼働上限、スキル
  - `tasks.yaml`: タスクの一覧、見積工数、必要スキル、先行タスク依存関係、完了期限
  - `calendar.yaml`: 週の標準稼働日、個別の祝日・特別休暇
- **FR-2 (メンバ定義)**:
  - メンバを一意に識別する `id`、表示名 `name`、稼働上限割合 `max_capacity`、保有スキル `skills` を定義できること。
- **FR-3 (タスク定義)**:
  - タスクを一意に識別する `id`、タイトル `title`、見積工数（時間）`estimate_hours`、必要スキル `required_skills`、先行タスク ID 一覧 `depends_on`、完了期限 `deadline` を定義できること。
- **FR-4 (カレンダー定義)**:
  - 週の標準稼働曜日 `workdays`、個別非稼働日 `holidays`（日付 `date`、名称 `name`）を定義できること。
- **FR-5 (検証 CLI)**:
  - 指定ディレクトリの `members.yaml`、`tasks.yaml`、`calendar.yaml` を一括検証し、結果に応じた終了コードを返せること。
- **FR-6 (タスク循環依存検知)**:
  - タスクの依存関係グラフにおいて、閉路（A -> B -> A 等の循環参照や自己参照 A -> A）が存在する場合に検知し、循環パスを含むエラーを出力して検証を失敗させること。
- **FR-7 (参照整合性検知)**:
  - タスクの `depends_on` に指定されたタスク ID が `tasks.yaml` 内に存在しない場合に検知し、未定義参照エラーを出力して検証を失敗させること。
  - タスクの `required_skills` に指定されたスキルを保有するメンバが `members.yaml` 内に 1 人も存在しない場合に検知し、担当可能メンバ不在エラーを出力して検証を失敗させること。
- **FR-8 (診断ヒントと位置特定)**:
  - 論理エラーのメッセージに、問題のあるタスク ID、キー、および具体的な解決ヒント（例: 存在するタスク ID の指定やタスクの追加）を含め、CLI ではエラーの発生位置（行番号）を特定可能にすること。

### 2.2 非機能要件 (NFR: Non-Functional Requirements)

- **NFR-1 (可読性と編集容易性)**: 人間および AI エージェントが直感的に読み書きできる標準的な YAML 形式であること。
- **NFR-2 (厳格な型・制約)**: 必須フィールドの欠落や型不正（工数の負数指定や日付形式の誤りなど）が静的に検知可能であること。
- **NFR-3 (YAGNI 原則)**: 初期 MVP では過度な入れ子構造や不要なメタデータを避け、最小限のフィールド構成とすること。
- **NFR-4 (診断可能性)**: CLI の検証エラーにはファイル名、行番号、該当キーを含めること。

## 3. データ構造・スキーマ定義 (Schema-Driven)

### 3.1 ディレクトリ配置

原本データは、プロジェクト内の指定ディレクトリ（デフォルト: `data/`）に配置します。

```text
data/
├── members.yaml      # メンバ情報
├── tasks.yaml        # タスク情報
└── calendar.yaml     # チームカレンダー・稼働日情報
```

---

### 3.2 `members.yaml` スキーマ

チームメンバおよびその制約を定義します。

```yaml
members:
  - id: alice
    name: "Alice"
    max_capacity: 1.0
    skills:
      - frontend
      - backend
  - id: bob
    name: "Bob"
    max_capacity: 0.8
    skills:
      - backend
      - devops
```

#### フィールド詳細 (`members[]`)

| フィールド名   | 型             | 必須     | デフォルト | 説明・制約                                                                            |
| :------------- | :------------- | :------- | :--------- | :------------------------------------------------------------------------------------ |
| `id`           | string         | **必須** | -          | メンバの一意な識別子（英数字・ハイフン・アンダースコア推奨）。重複不可。              |
| `name`         | string         | **必須** | -          | メンバの表示名。                                                                      |
| `max_capacity` | number         | 任意     | `1.0`      | 稼働上限割合。`0.0 < max_capacity <= 1.0` の範囲であること（例: `0.8` は 80% 稼働）。 |
| `skills`       | list of string | 任意     | `[]`       | メンバが保有するスキル名のリスト。                                                    |

---

### 3.3 `tasks.yaml` スキーマ

計画対象のタスク、工数、制約を定義します。

```yaml
tasks:
  - id: task-api
    title: "REST API 設計と実装"
    estimate_hours: 16
    required_skills:
      - backend
    depends_on: []
    deadline: "2026-09-20"
  - id: task-ui
    title: "フロントエンド画面実装"
    estimate_hours: 24
    required_skills:
      - frontend
    depends_on:
      - task-api
    deadline: "2026-09-25"
```

#### フィールド詳細 (`tasks[]`)

| フィールド名      | 型             | 必須     | デフォルト | 説明・制約                                          |
| :---------------- | :------------- | :------- | :--------- | :-------------------------------------------------- |
| `id`              | string         | **必須** | -          | タスクの一意な識別子。重複不可。                    |
| `title`           | string         | **必須** | -          | タスクの名称・説明。                                |
| `estimate_hours`  | number         | **必須** | -          | 見積工数（時間単位）。正の数値（`> 0`）であること。 |
| `required_skills` | list of string | 任意     | `[]`       | タスク遂行に必要なスキル名リスト。                  |
| `depends_on`      | list of string | 任意     | `[]`       | 先行して完了すべきタスクの `id` 一覧。              |
| `deadline`        | string (date)  | 任意     | `null`     | タスクの完了期限日付。`YYYY-MM-DD` 形式であること。 |

---

### 3.4 `calendar.yaml` スキーマ

稼働日計算の前提となる週稼働曜日および祝日・休暇を定義します。

```yaml
calendar:
  workdays:
    - mon
    - tue
    - wed
    - thu
    - fri
  holidays:
    - date: "2026-09-15"
      name: "敬老の日"
    - date: "2026-09-23"
      name: "秋分の日"
```

#### フィールド詳細 (`calendar`)

| フィールド名      | 型             | 必須     | デフォルト                  | 説明・制約                                                                                  |
| :---------------- | :------------- | :------- | :-------------------------- | :------------------------------------------------------------------------------------------ |
| `workdays`        | list of string | 任意     | `[mon, tue, wed, thu, fri]` | 週の標準稼働日。値は `mon`, `tue`, `wed`, `thu`, `fri`, `sat`, `sun` のいずれか。重複不可。 |
| `holidays`        | list of object | 任意     | `[]`                        | 個別の祝日・会社休日・特別休暇のリスト。                                                    |
| `holidays[].date` | string (date)  | **必須** | -                           | 非稼働日の日付。`YYYY-MM-DD` 形式（実在する日付であること）。重複不可。                     |
| `holidays[].name` | string         | 任意     | `""`                        | 祝日・休暇の名称。                                                                          |

## 4. 受入基準とテストシナリオ (TDD 連携)

### シナリオ 1: 正常系原本データの定義と読み込み (AC-1, AC-2, AC-3)

- **前提 (Given)**:
  - 上記スキーマに準拠した `members.yaml`, `tasks.yaml`, `calendar.yaml` が存在する。
- **操作 (When)**:
  - スキーマバリデータまたはデータローダーで各ファイルを読み込む。
- **期待結果 (Then)**:
  - エラーなく解析され、定義された通りのメンバ一覧、タスク一覧、カレンダー設定オブジェクトとして取得できること。

### シナリオ 2: 必須フィールド欠落時の検知

- **前提 (Given)**:
  - `tasks.yaml` 内のタスクに `estimate_hours` が存在しない。
- **操作 (When)**:
  - スキーマバリデータで検証を実行する。
- **期待結果 (Then)**:
  - 検証が失敗し、該当タスクの `id` と欠落している必須キー名（`estimate_hours`）を含むエラーが報告されること。

### シナリオ 3: 不正な型・制約違反の検知

- **前提 (Given)**:
  - `members.yaml` で `max_capacity` に `1.5`（1.0 超）や `-0.2`（0 以下）が指定されている。
  - または `tasks.yaml` で `deadline` に `2026-02-30`（実在しない日付）や `invalid-date` が指定されている。
  - または `calendar.yaml` で `holidays` に同一の `date` が重複して指定されている、もしくは実在しない日付（例: `2026-02-30`）が指定されている。
  - または `calendar.yaml` で `workdays` に重複する曜日が指定されている。
- **操作 (When)**:
  - スキーマバリデータで検証を実行する。
- **期待結果 (Then)**:
  - 検証が失敗し、許容範囲外・重複・形式不正である旨のエラーが報告されること。

### シナリオ 4: CLI からの一括検証

- **前提 (Given)**:
  - 指定ディレクトリに `members.yaml`、`tasks.yaml`、`calendar.yaml` が存在する。
- **操作 (When)**:
  - `npm run validate -- <directory>` を実行する。
- **期待結果 (Then)**:
  - すべてのファイルが有効な場合は終了コード `0` と成功メッセージを返すこと。
  - 検証エラーがある場合は終了コード `1` を返し、`<file>:<line>: <message>` 形式でファイル名、行番号、キー名を含む診断を標準エラー出力へ返すこと。

### シナリオ 5: タスク依存関係と参照の論理整合性検証 (AC-1, AC-2, AC-3, AC-4)

- **前提 (Given)**:
  - 各原本ファイルの構文および基本型が妥当である。
- **操作 (When)**:
  - 論理整合性バリデータまたは一括検証 CLI を実行する。
- **期待結果 (Then)**:
  - **循環依存の検知 (AC-1)**: タスクの `depends_on` に閉路（例: `A -> B -> A`、`A -> B -> C -> A`、自己参照 `A -> A`）が存在する場合、検証が失敗し、循環パス（例: `task-a -> task-b -> task-a`）と循環解消のヒントを含むエラーを出力すること。
  - **未定義タスク参照の検知 (AC-2)**: `depends_on` に同一 `tasks.yaml` 内に存在しないタスク ID が指定されている場合、検証が失敗し、未定義タスク ID と解決ヒント（存在するタスク ID を指定するかタスクを追加する等）を含むエラーを出力すること。
  - **未定義スキル参照の検知 (AC-3)**: タスクの `required_skills` に `members.yaml` のどのメンバも保有していないスキル名が指定されている場合、検証が失敗し、担当可能メンバが不在である旨と解決ヒントを含むエラーを出力すること。
  - **CLI での診断出力 (AC-4)**: CLI 実行時、上記論理エラーが該当ファイル名（`tasks.yaml`）と該当行番号付きで出力され、終了コード `1` を返すこと。

## 5. 制約事項・スコープ外 (Out of Scope)

YAGNI 原則（不要な複雑性の排除）に基づき、以下の項目は本仕様のスコープ外とします。

1. **タスクの複数メンバ同時担当**:
   - 1 つのタスクを複数メンバで分担するスキーマは含めません（タスクは 1 人が担当することを前提）。
2. **日単位より細かい粒度のスケジューリング**:
   - 工数は「時間（h）」、カレンダーや期限は「日（YYYY-MM-DD）」単位とし、時間帯（HH:MM）レベルの指定は見送ります。
3. **実績工数（Actuals）の混入**:
   - 原本 YAML は「計画の前提条件」のみを保持します。作業実績や日々の消化工数は原本に直接上書きせず、別管理（Milestone 3）とします。

## 6. 代替案と設計判断

- **単一ファイル（`taskweave.yaml`） vs 分割ファイル（`members.yaml`, `tasks.yaml`, `calendar.yaml`）**:
  - **採択**: 関心事ごとの分割ファイル。
  - **理由**: タスク一覧の追加・変更が最も頻繁に行われるのに対し、メンバ定義やカレンダーは更新頻度が低いため、Git 上でのコンフリクトを最小化し、エージェントが各ファイルを独立して編集・理解しやすくするため。

## 7. 検証 CLI

検証 CLI は次の形式で実行します。

```sh
npm run validate -- [directory]
```

`directory` の省略時は `data/` を対象とします。指定ディレクトリにある 3 つの原本 YAML をすべて読み込み、構文・型制約およびファイル間の論理整合性（循環依存、未定義参照）を検証します。すべて有効なら終了コード `0`、1 つでも読み込み、スキーマ違反、または論理整合性違反があった場合は終了コード `1` を返します。診断は `<file>:<line>: <message>` 形式で標準エラー出力へ出力します。
